Topic: layout of the combined diagram (all_packages.puml, step 09)

State at session start: all 17 CityGML 3.0 modules processed (steps 01-08),
step 09 combined diagram existed (landscape, core package wherever Graphviz

Requests and outcomes, in order:

1. "Can core.xsd be placed in the center of all_packages.puml without
   breaking the !include method?"
   - Answer: includes are safe, but PlantUML has no absolute positioning;
     only layout BIAS via hidden package-to-package links is possible.
   - Verified on local PlantUML 1.2020.02: arrows between packages work,
     hidden ones only affect layout.
   - Implemented in step09: plain `core -[hidden]- <pkg>` for all 16 other
     modules. Result: diagram ~17% narrower (19757 -> 16378 px wide) but
     core stayed pinned top-left (generalization ranks dominate).

2. "Distribute the other modules around core: split into groups, assign
   groups to directions left/right/up/down."
   - Implemented group rotation, measured all variants (SVG cluster coords):
     * 4-way incl. `up`: contradicts generalization ranks (core's subclasses
       must be below it) -> giant looping edges. `up` dropped permanently.
     * left/right/down rotations: chaotic — core at 18-82% of diagram width
       depending on group composition; a tie in class counts (building vs
       dynamizer) flipped core from 55% to 21%. Added deterministic
       tie-break by package name. Best: 55%.
   - User rejected the result aesthetically ("i didn't like the final
     product").

3. "Vertical style?" (question only, no implementation)
   - Explained `left to right direction` rotates the layout 90 deg;
     parked for later (implemented in step 5 below).

4. "Core at the bottom, other modules ordered upward by their connection
   count to core, tree-like, use dash length for distance. What do you
   think?"
   - Core at bottom: impossible. No bottom-to-top direction in PlantUML,
     and hundreds of generalization edges force core upward. Root-at-top
     is also UML convention.
   - The rest (connectivity-count ordering + dash-length layers): good,
     works WITH Graphviz. User approved the reversed version (core at top).

5. Implemented connectivity layering in step09_all_packages.py:
   - Per module, count lines referencing `core:` in its .puml (core-typed
     attributes + stub declarations + inheritance/relation edges):
     gen 18, tran 13, con 12, app 9, dyn/vers 8, bldg/dem 6, grp 5,
     wtr 4, brid 3, veg/tun/pcl/luse/frn 2.
   - Distinct counts compressed into ~sqrt(n)=4 layers, equal counts share
     a layer; one hidden link per module with dash count = layer
     (`core -[hidden]-- gen` ... `core -[hidden]----- frn`; dash count maps
     to Graphviz minlen).
   - Tried and rejected (documented in AGENTS.md):
     * class-level hidden links -> Graphviz/smetana CRASHES on this
       diagram size ("dot/GraphViz has crashed"), even 16 edges, no minlen;
     * package chain (core -> gen -> tran -> ... -> frn): renders but ugly
       diagonal sprawl.
   - Result: weak but real layering (L1 modules ~47-56% height vs L4
     ~47-94%), tidy landscape cascade, 19010x3344 px.

6. "Still landscape — order them up to down."
   - Added `left to right direction` to step09 output -> PORTRAIT,
     6933x11323 px. Core at top (7% height, cluster spans left edge like
     a trunk), 16 modules stacked below — most tree-shaped result so far.
   - Measured: without the hidden links core drifts to the MIDDLE (6th of
     17 clusters vertically) -> the connectivity links now serve as the
     anchor keeping core at top; they stay.
   - Honest caveat: vertical module order only loosely follows the
     connectivity layers (vers at bottom despite layer 2); vertical order
     within ranks is Graphviz crossing-minimization, not controllable.
